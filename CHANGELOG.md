# Changelog

## [Unreleased]

### Bug Fixes

- **A typed condition written before `.delete()`, `.update()`, `.softDelete()` or `.restore()` no longer keeps the select alias.** A column of the main alias was qualified when the condition was added, so `createQueryBuilder('user').whereIsInTyped((q) => q.id, ids).delete()` ran `DELETE FROM "users" WHERE "user"."id" IN (…)`, which the database rejects (`missing FROM-clause entry for table "user"`): an UPDATE or DELETE has no alias. The typed where methods now leave the alias of a main-alias column to the moment the SQL is built, so it is `"user"."id"` on a select and `"id"` on an UPDATE or DELETE. Conditions on joined aliases, select, order by, group by and having are written as before.

## [3.4.0] - 2026-11-26

### New Features

- **`enableUnboundParameterGuard`** (also from `typeorm-extensions/helpers`): an opt-in check of the SQL every query builder runs for a `:name` or `:...name` parameter without a value, which TypeORM leaves in the SQL as written and the database rejects with a syntax error that doesn't name it. The query throws or rejects with an `UnboundParameterError` naming the parameter before it runs, or, with `mode: 'warn'`, runs and is reported to `onViolation`. The SQL is read as the database reads it: casts (`::text`), literals, quoted names, comments, Oracle's `:1` and PostgreSQL slice bounds (`tags[1:n]`) are not parameters. `findUnboundParameters(sql, driver)` is the check on its own.

## [3.3.1] - 2026-11-25

### Bug Fixes

- **A loaded `@CalculatedColumn` value no longer counts as a change on `save`.** `save` compared the property with the reloaded row, where a calculated property is always undefined, so a loaded value (a count, a flag) marked it changed. On TypeORM 0.3.12 saving an entity with no other change then ran an UPDATE with nothing to SET and threw `UpdateValuesMissingError`; on later versions the property was only compared for nothing. A `transformer` of its own still converts the selected value; its `to` is no longer called.

## [3.3.0] - 2026-11-24

### New Features

- **`whereExpression` / `andWhereExpression` / `orWhereExpression`**: a condition on an SQL expression rather than a column (`coalesce(…)`, `lower(…)`, `AT TIME ZONE … ::date`, arithmetic), written as is and compared through a TypeORM find operator, as `whereTyped` compares a column, or through an SQL condition with its value. A find operator's values get unique parameter names, so a condition on `coalesce(a, b)` no longer has to name its parameter by hand. On `SelectQueryBuilder`, `UpdateQueryBuilder`, `DeleteQueryBuilder`, `SoftDeleteQueryBuilder` and in `Brackets`. An empty expression, or a condition that is neither, throws a `TypeError` instead of being left out.
- **`Or(…operators)`** (also from `typeorm-extensions/helpers`): a column matches when any of the operators matches, `(a OR b)`, in one `whereTyped` call instead of `Brackets`. TypeORM 0.3.12 has no `Or`; the typed where methods and `whereExpression` write this one, and TypeORM's own where the version has it, the same way on every version. `Not(Or(…))` is `NOT(a OR b)`, and `Or` nests and goes inside `And(…)`. A JSON path compared through an `Or` is cast to the type of the first value it holds.

## [3.2.2] - 2026-11-24

### Bug Fixes

- **`input: 'page' | 'offset' | 'any'`** on `applyPagination`, `getLimitAndOffset`, `getManyWithTotals` and `getRawManyWithTotals`, and in `setPaginationDefaults`: what a read takes from its filter. Since 3.2.0 a filter without `page` and `pageSize` is read by its `offset` / `limit`, so a request filter carrying a `limit` its list doesn't declare paged by it, past the `pageSize` its validation caps. With `input: 'page'` a read takes only `page` / `pageSize`, as before 3.2.0; with `'offset'` only `offset` / `limit`. `'any'`, the default, reads as 3.2.0 does. An application whose filters come from requests sets `setPaginationDefaults({ input: 'page' })` and passes `{ input: 'offset' }` where it pages by offset.
- **Strict order input refuses a dotted name it can't order by.** With `enableStrictOrderInput`, a `field` with dots that is not an embedded column's path (`user.firstName`, `posItem.name`), or a `tableAlias` with dots (`a.b`), throws an `InvalidOrderError`. Both passed the check and were then quoted as names the database doesn't have, so the query failed when it ran instead of being refused as a bad order. An embedded column's path (`address.city`) still orders by its column.

## [3.2.0] - 2026-11-24

Tested as the release candidates `3.2.0-rc.0` and `3.2.0-rc.1`.

### New Features

- **`maxPageSize`** on `getLimitAndOffset` / `normalizePageSize`: a larger `pageSize`, or default, is lowered to it, so a request can't read a whole table in one page. Ignored when not a number of at least 1.
- **`applyPagination`, `getManyWithTotals`, `getRawManyWithTotals`, `getManyWithCursor` and `getRawManyWithCursor` take `defaultPageSize` and `maxPageSize`**, so a query with its own default or cap no longer has to compute the page by hand. The `page` / `pageSize` they return are the ones read.
- **`applyPagination`, `getLimitAndOffset`, `getManyWithTotals` and `getRawManyWithTotals` take `{ offset, limit }`** as well as `{ page, pageSize }`: the rows to skip and the rows to read, under the same `defaultPageSize` / `maxPageSize`. A negative or non-numeric offset reads from the first row, and the `page` they return is the page the offset falls in. A filter that gives `page` or `pageSize` is still read by them; one that gives only `offset` / `limit` used to read the first page, and now reads the rows it names.
- **`firstPage: 0 | 1`**: pages counted from 0 (`page: 0` is the first page) or from 1, the default. The `page` a read returns counts the same way.
- **`maxPage`**: the last page a read may ask for. A later page, or an offset past its first row, throws a **`PageOutOfRangeError`** (a `RangeError` with `page` and `maxPage`) before the query runs, so a client can't make the database skip a whole table.
- **`setPaginationDefaults({ firstPage, defaultPageSize, maxPageSize, maxPage })`** and `getPaginationDefaults()` (from `typeorm-extensions/helpers`): the options every paginated read takes when its call doesn't give its own, so an application whose pages start at 0, or whose lists stop at 100 rows a page, says so once. An option given in the call still wins.
- **`iterateWithCursor({ batchSize, orderBy })` and `iterateRawWithCursor`**: every row of a query in batches, an async iterator over the `getManyWithCursor` / `getRawManyWithCursor` pages, for work over a large set such as a sync or a backfill. Each batch costs the same however deep it is, and rows that leave the query while it runs (processed, deleted) don't make later batches skip rows, as they do with OFFSET. `batchSize` is read as given, whatever `setPaginationDefaults` says; a `batchSize` below 1 or not whole, or a key that is not a column, throws a `TypeError` at the call.

## [3.1.0] - 2026-11-23

### New Features

- **`enableStrictOrderInput()` / `disableStrictOrderInput()`** (from `typeorm-extensions/helpers`): with it on, every `applyOrder` / `applyOrderFilter` refuses an order whose `field` or `tableAlias` is not a name (`firstName`, `user.firstName`) or whose `nulls` is not `first` / `last` / `NULLS FIRST` / `NULLS LAST`, before the query is built. Off by default, where such an order is still taken as given: its names quoted as one identifier each, an unknown `nulls` left out. `direction` and `isReversed` stay lenient. Turn it on once where the extensions are loaded when orders come from requests, so a caller can't forget it.
- **`InvalidOrderError`**, a `TypeError` with the `part` (`order`, `field`, `tableAlias`, `alias`, `nulls`) and the `value` it rejected: thrown by the strict check, and now also for an order without a string `field` and for an expression with `useQuotes: false`, which threw a plain `TypeError`. An application can answer it as a bad request in one place.
- **`applyOrderFilter` takes the orders themselves**: a list (`applyOrderFilter(filter.orderedBy)`) or one order, as well as an `{ orderBy }` filter.
- **`getLimitAndOffset` and `normalizePageSize` are exported** from `typeorm-extensions/helpers`, with a `defaultPageSize` option for a filter that gives no page size (10 when not given; a default below 1 is 10 too).

## [3.0.0] - 2026-11-23

Tested as the release candidates `2.2.0-rc.1` … `2.2.0-rc.17` and `3.0.0-rc.0` … `3.0.0-rc.10`; the release is 3.0.0 because `returningTyped` changed shape.

A major version. Every export of 2.1.0 is still there except `applyPaginationFilter`, `tableHelper`'s `jsonColumn` / `jsonPath` and the `JsonFieldRest` type, and `returningTyped` changed shape; a few calls that worked now throw or read differently. **Breaking Changes** lists all of it, and [Upgrading from 2.x](https://koenigstag.github.io/typeorm-extensions/docs/getting-started/upgrading-from-2) walks through it. It also carries the MIT license prepared for 2.1.1, which was never published.

### Breaking Changes

- **`applyPaginationFilter` is removed**: `applyPagination` takes the same arguments and gives the same result. `getManyWithTotals` doesn't call either method through the query builder, so a method an application patches under one of these names doesn't change how it pages.
- **`tableHelper.jsonColumn` / `jsonPath` are removed**: `t.jsonText((r) => r.metadata.role)` in place of `t.jsonColumn('metadata', '->>', 'role')` and `t.json((r) => r.metadata.settings)` in place of `->`. Their result is in parentheses. In a typed where the callback goes into the JSON column itself, `whereTyped((u) => u.metadata.role, …)`, in place of a `jsonPath` fragment.
- **`returningTyped` returns an object of output names**: `returningTyped(t => ({ id: t.id, status: t.status }))` in place of `returningTyped(t => [t.id, t.status])`. The rows in `execute()`'s `raw` are keyed by those names (`{ id, status }`), not by the database column names, and hold exactly the listed outputs: TypeORM no longer adds the generated columns of an INSERT. A value is a column (`t.address.city`, `i.user` for a relation with one join column) or an SQL expression built from them (`` `${t.status} = 'done'` ``). On PostgreSQL 18+ `old` and `new` give the row before and after the write (`({ old, new: next }) => ({ changed: `${old.status} IS DISTINCT FROM ${next.status}` })`); elsewhere they throw a `TypeError`. A list, an empty object or a value that is neither a column nor a string throws a `TypeError`.
- **`JsonFieldRest` is removed**: only `jsonColumn` / `jsonPath` used it.
- **Typed select, order, group by and distinct quote the keys of an alias without metadata** (a subquery, a CTE, a table that isn't an entity), as typed where methods do; see Bug Fixes. A column raw SQL names without quotes (`SELECT id AS userId`) is `userid` on PostgreSQL, so a camelCase key for it no longer matches: quote it in the SQL, `AS "userId"`.
- **`ListWithTotals` and `ListWithCursor` have new required fields**, `hasMore` and `pageSize`, and `page` for `ListWithTotals`. Code that reads them needs no change; a mock or a wrapper that builds one adds them.
- **A descending cursor made by 2.x is refused once** with `InvalidCursorError`: cursors now name the direction of their keys (`-id`). Ascending cursors keep working.
- **Inputs that throw a `TypeError` instead of being dropped or misread**: a params object after the condition with more than one key or none (`whereTyped(u => u.id, '=', { id, email })`); `applyOrder` with `useQuotes: false` and an expression in place of a column name; an order without a `field`; a value list for `whereIsIn` / `whereIsAny` / `innerJoinUnnest` that is neither a list nor one value; the array conditions on a database other than PostgreSQL.
- **`getManyWithTotals` holds two pool connections** for the length of the call without a query runner of its own: the count and the page run at the same time.
- **`whereSimilarTyped` (and `and…` / `or…`) and `addSimilarityScoreTyped` throw a `TypeError` on a database other than PostgreSQL**, even for a blank term: there `%` is the modulo operator, so `col % 'jon'` ran and matched no row. A query builder without a connection is taken for PostgreSQL, and CockroachDB passes. `addSimilarityScoreTyped` given a callback that selects several columns asks for `options.combine` instead of throwing that it takes one column.

### New Features

- **Trigram search as a filter, a score and an order**, three pieces that don't touch each other (PostgreSQL, `pg_trgm`):
  - **`orderBySimilarityTyped` / `addOrderBySimilarityTyped`**: the most similar first, `DESC NULLS LAST`, so a row with NULL columns no longer sorts above every match. The score is selected under a generated lower-case alias (or a validated `alias`) and ordered by it, which works with `take` / `skip` and joined collections. One form replaces the ORDER BY, the other appends to it. A blank term adds nothing, so the query keeps its order. `distance: true` orders by `col <-> :term` (`<->>`, `<->>>` for the word scores) ascending, which a GiST `gist_trgm_ops` index serves as an `Index Scan … Order By` with `limit`.
  - **`whereSearchTyped({ similar, substring })`**: `similar` adds a trigram condition per column to the same OR group, `(col ILIKE :pattern OR col % :term …)`, taking the options of `whereSimilarTyped` (`operator`, `minScore`, `operator: false`); `substring: false` leaves the ILIKE conditions out. Without `similar` the method is unchanged on every database.
  - **`whereSimilarTyped`**: the strict word operators `%>>` and `<<%`; `minScore`, `(col % :t AND similarity(col, :t) >= :min)` with the score each operator compares, bound as a parameter; `operator: false` for the score alone, `similarity(col, :t) >= :min` (or `function: 'word_similarity'` / `'strict_word_similarity'`), for a cutoff below the session threshold; `unaccent` and `minLength`.
  - **`addSimilarityScoreTyped` on several columns**: `combine: 'greatest'` (`GREATEST(s1, s2)`) or `'sum'` (`COALESCE(s1, 0) + COALESCE(s2, 0)`), `{ column, weight }` selectors, raw `{ sql }` expressions, `nullScore` for a row whose columns are all NULL, and `unaccent`.
  - A [Fuzzy search with pg_trgm](https://koenigstag.github.io/typeorm-extensions/docs/examples/fuzzy-search) page: ranking bands built from `Sql`, which indexes serve which form, a lower threshold for one transaction with `set_config(…, true)`, and keyset pages by score.
- **`{ alias }` keys in `getRawManyWithCursor`**: `orderBy: [{ alias: 'score', direction: 'DESC' }]` takes the SQL of the selection with that alias as the key, with its parameters, so a score selected by `addSimilarityScoreTyped` or any `addSelect(sql, alias)` pages without its SQL written twice.
- **`json` / `jsonText` on `tableHelper`**: a value inside a JSON column with the path as a callback, `t.jsonText((r) => r.metadata.settings.theme)` → `("user"."metadata" -> 'settings' ->> 'theme')`; `json` uses `->` on every key. The keys are checked against the column's type, a key of digits is an array index, and the result is in parentheses. With a `driver` they write MySQL's `JSON_EXTRACT` / `JSON_UNQUOTE` and SQLite's `$` paths. They replace `jsonColumn` and `jsonPath`, see **Breaking Changes**.
- **`hasMore` on both paginated results**: `getManyWithTotals` returns `offset + list.length < total`, and with `disableTotalsCalculation` reads the page one row longer instead of counting — the extra row is dropped from `list` and only answers `hasMore`, so no `COUNT` query runs and the flag is still known. `null` only with `loadAll`, where the page is every row. `getManyWithCursor` returns a boolean the same way, from the `pageSize + 1` rows its keyset query already loads.
- **`orderBy` on both paginated results, with `includeOrderBy: true`**: the ORDER BY the page was read in, as `OrderType[]`, for logs and debugging. Left out by default, so a result passed on as an API response doesn't carry SQL. For `getManyWithTotals` these are the selectors the ORDER BY was given (`user.createdAt` for an entity property `applyOrder` ordered by, `"cte"."total"`, a generated `array_position_…` alias, a raw expression), not properties of the entity. Without an explicit order it is the `orderBy` of `@Entity`, like the SQL; empty with the `disable-global-order` option. `getManyWithCursor` returns its `orderBy` columns followed by the appended primary key, as `alias.property` (`user.createdAt`): the order its cursors encode.
- **`page` and `pageSize` on both paginated results**: the values the page was read with, after the defaults. `getManyWithTotals` returns `page: 1` for a missing page or one below 1 and `pageSize: 10` for a missing size or one below 1, and `null` for both with `loadAll`; `getManyWithCursor` returns the `pageSize` rounded down, `10` when it was missing or below 1. A response can pass them on without repeating the defaults of the library. `applyPagination`, `getManyWithTotals`, `getRawManyWithTotals` and `getManyWithCursor` read a numeric string, such as an unparsed query parameter `'20'`, as a number and round a fraction down, so the results hold numbers; with `disableTotalsCalculation`, `pageSize: '20'` no longer reads `'20' + 1` = 201 rows.
- **`getRawManyWithCursor`**: `getManyWithCursor` for raw rows, ordered by SQL expressions, so a computed value can be a key (`CASE "member"."role" WHEN 'owner' THEN 0 ELSE 1 END`). The primary key of the main alias is appended when the query is on an entity without GROUP BY or DISTINCT; otherwise the last key has to be unique per row. The cursor names its keys by a hash of their SQL and carries no SQL, timestamp keys keep the database's precision, and the columns read for the cursor are left out of the rows.
- **`getRawManyWithTotals`**: `getManyWithTotals` for raw rows, with the same result (`total`, `hasMore`, `orderBy`), concurrency and options except `useTakeAndSkip`: raw rows are paged with LIMIT / OFFSET. `total` counts the rows the query returns: the query is counted as a subquery, `SELECT COUNT(*) FROM (query)`, so a grouped query counts its groups and HAVING applies. `countExpression` counts with an expression instead (`COUNT(DISTINCT "order"."user_id")`), without GROUP BY and HAVING.
- **`typed<Root>()`** sets the root of the typed callbacks once for a query, instead of passing it to each call (`whereTyped<Joins>(…)`): `query.typed<{ checkin: CheckIn; event: Event }>().whereTyped((q) => q.event.eventType, '=', type)`. Type-only; the root carries through the chain, TypeORM's methods and this library's included, and `getMany()` still returns the entities. With `strictParams` the parameters of these calls are checked, which an explicit type argument turns off. It marks the builder, not its entity: it returns `WithTypedRoot<SelectQueryBuilder<Entity>, Root>`, and the typed methods' default root is `TypedRoot<Entity, this>`, the root of that mark, else the entity. The marked builder goes wherever the unmarked one does: a `SelectQueryBuilder<ObjectLiteral>` parameter, a helper generic over the entity (`<T>(qb: SelectQueryBuilder<T>)` infers `T` as the entity), and a cast that compiles without the mark, such as `dataSource.createQueryBuilder().typed<Joins>() as SelectQueryBuilder<Row>`. A helper generic over the entity can call `typed()` itself and return the builder as its `SelectQueryBuilder<T>`. It works on a `SelectQueryBuilder<any>` too, and declaration files (`declaration: true`) name a marked builder by `WithTypedRoot`. A builder of a marked entity, `SelectQueryBuilder<WithTypedRoot<Entity, Root>>`, takes the root too. The methods of this library that returned `SelectQueryBuilder<Entity>` on a select query (`selectTyped`, `orderByTyped`, the typed joins, `distinctOnTyped`, `whereIsIn` / `whereIsAny` and their variants, `applyOrder`, `applyPagination`) return `this`, so the mark carries through them. `from()` and `addFrom()` keep the root, so it may go before them (`dataSource.createQueryBuilder().typed<Joins>().from(CheckIn, 'checkin')`); a subquery starts without it; a second call replaces the root.
- **`groupByTyped` / `addGroupByTyped`**: GROUP BY with typed callbacks on `SelectQueryBuilder`. One callback may select several columns (`user => [user.id, user.email]`), and columns of joined relations work too. Like `orderByTyped`, the key is `alias.property`, which TypeORM maps to the column, or with `useQuotes` the quoted database column, which a subquery in FROM needs. A JSON column groups as a whole (`jsonb` on PostgreSQL), while a path into one throws a `TypeError`, as in select, order and distinct. The callback starts at the root set with `typed<Root>()`, else at the entity.
- **`havingTyped` / `andHavingTyped` / `orHavingTyped`**: HAVING on an aggregate of a typed property, `havingTyped('COUNT', u => u.images.id, '>=', 2)`. `COUNT`, `COUNT DISTINCT`, `SUM`, `AVG`, `MIN`, `MAX`, and `'*'` for `COUNT(*)`. Parameters as in `whereTyped`; with `strictParams` the value is a number for counts, sums and averages and the column's value for `MIN` / `MAX`. The callback starts at the root set with `typed<Root>()`, else at the entity.
- **`leftJoinAndMapOneTyped` / `innerJoinAndMapOneTyped` / `leftJoinAndMapManyTyped` / `innerJoinAndMapManyTyped`**: TypeORM's map joins with the property to map to picked by a typed callback instead of an `'alias.property'` string: `leftJoinAndMapOneTyped((u) => u.profile, Profile, 'profile', 'profile.userId = user.id')` is `leftJoinAndMapOne('user.profile', …)`. The property may be any property of the root, a relation or one declared for the mapped data; with an alias-keyed root, `(q) => q.photo.owner` is `'photo.owner'`, a property of a joined alias. The joined data is what TypeORM's methods take: an entity, a relation, a table name or a subquery factory; TypeORM's `mapAsEntity` isn't passed on. The callback starts at the root set with `typed<Root>()`, else at the entity.
- **`whereNotExists` / `andWhereNotExists` / `orWhereNotExists`**, and `whereExists` / `andWhereExists` / `orWhereExists` on update, delete and soft delete / restore queries: TypeORM has `EXISTS` on `SelectQueryBuilder` only, and no `NOT EXISTS`. The SQL is TypeORM's, so `NOT EXISTS` is the negation of its `whereExists`, except with a HAVING in the subquery: its GROUP BY stays, where TypeORM drops it and the HAVING then aggregates the whole subquery. A method is added only where the builder lacks it: TypeORM's own `whereExists` stays. The subquery's parameters get unique names, so two subqueries that both use `:status` keep their own values; with TypeORM's `whereExists` the value set last wins.
- **A factory for `whereExists` / `whereNotExists`** and their `and…` / `or…` forms, on every builder that has them: `andWhereNotExists((sub) => sub.select('1').from(Ticket, 'ticket').where(…))`. The factory gets a new query builder on the query's connection and query runner, so the subquery runs in the same transaction, and its parameters get unique names. TypeORM's own `whereExists` / `andWhereExists` / `orWhereExists` on `SelectQueryBuilder` take a factory too: the extension wraps them, and a query builder still goes to TypeORM's method.
- **`existsSql` / `notExistsSql`**: `EXISTS (subquery)` and `NOT EXISTS (subquery)` as SQL, on select, update, delete and soft delete / restore queries and on the builder `Brackets` passes, for a place the `where*Exists` methods don't reach: an `OR` group, a `CASE`, a selection, an ordering, a join condition, `FILTER (WHERE …)`. `.where((qb) => \`"user"."id" = :id OR ${qb.existsSql((sub) => sub.select('1').from(Ticket, 'ticket').where(…))}\`, { id })`, through TypeORM's `where` with a function. The subquery is built as for `whereExists`, from a query builder or a factory; its parameters get unique names and are set on the query when the method is called, so the SQL needs no parameters of its own.
- **`whereRelationExistsTyped` / `whereRelationNotExistsTyped`** (and `and…` / `or…`): `EXISTS` / `NOT EXISTS` over a relation picked by a typed callback, with the join condition from the relation's metadata: one-to-many, many-to-one, one-to-one and many-to-many through the junction table. A callback narrows the related rows; the join condition is added after it and can't be dropped or bypassed by its `where` / `orWhere`. Subquery parameters get unique names. The callback starts at the root set with `typed<Root>()`, else at the entity.
- **`timeZone` in `applyPeriodFilter` / `applyPeriodFilterTyped`**: reads a date (`'2024-01-31'`) and a date-time without an offset (`'2024-01-31 10:00'`) as the wall clock of an IANA time zone, so a period of days is the user's days: `{ periodFrom: '2024-01-01', periodTo: '2024-01-31' }` in `America/New_York` is `>= 2024-01-01T05:00Z AND < 2024-02-01T05:00Z`. Converted in JavaScript (`Intl`), so the column stays bare in SQL and keeps its index, on every database; daylight saving time as PostgreSQL's `AT TIME ZONE` handles it. `Date`s stay as they are, strings with an offset (`Z`, `+02:00`) become that instant, other strings and unknown zones throw a `TypeError`.
- **`leftJoinLateral` / `innerJoinLateral`**: `LEFT JOIN LATERAL` and `INNER JOIN LATERAL`, which TypeORM doesn't have, with a query builder, a factory or raw SQL as the subquery and `ON TRUE` by default. A query builder's or a factory's parameters get unique names, so a `:status` in the subquery doesn't clash with one in the outer query. They go through TypeORM's own subquery-join path. PostgreSQL, CockroachDB, MySQL 8.0.14+ and Oracle.
- **`innerJoinUnnest(field, array, arrayType?)`**: keeps the rows whose column is in an array by joining `SELECT DISTINCT unnest(CAST(:array AS type[]))`, the same rows as `whereIsAny` with a plan that can start from the array. The array type defaults to the array of the column's type, also for a quoted path such as `tableHelper` writes (`"user"."id"`); it is required for a field that isn't an entity column and for an enum column. An empty array matches no row and needs no array type. PostgreSQL and CockroachDB.
- **`fromUnion` / `addCommonTableExpressionUnion`**: a UNION (or `UNION ALL`) of query builders as the FROM of a query or as a common table expression. The parameters of each part get unique names: pasting `getQuery()` and merging `getParameters()` lets two parts with a `:status` each read the last value, without an error. Raw SQL parts read the outer builder's parameters. On SQLite a part with an ORDER BY or a LIMIT, as of an entity's default `orderBy`, is wrapped in `SELECT * FROM (…)`, and the others stay bare, so a recursive CTE works there too. A part built with `subQuery()` goes in without the parentheses it writes around itself, which SQLite rejects in a UNION.
- **`@GeneratedColumn`**: `@Column` for a column the database computes (`GENERATED ALWAYS AS (…) STORED`), with `insert` and `update` off. A plain `@Column` over such a column sends whatever the entity holds in `save`, `insert` and `update`, and the database rejects it; `asExpression` only describes the column for schema sync and doesn't stop that, in TypeORM 0.3 or 1.x. Every other column option applies (`select: false`, `name`, and `asExpression` / `generatedType` for schema sync); `insert`, `update` and `readonly` aren't accepted. Exported from the package root and from `typeorm-extensions/helpers`. The docs compare it with `@CalculatedColumn` and TypeORM's `@VirtualColumn`, with a use case for each.
- **`@CalculatedColumn` and `addSelectCalculated`**: an entity property that a query fills with an SQL expression of its own. The decorator declares no column of the table (schema sync leaves it out, it is never inserted or updated, and TypeORM never selects it by itself); `addSelectCalculated(expression or subquery, property, alias?)` selects into it under the key TypeORM hydrates from, with the property checked against the entity type. The value is converted by the property's type, so a `number` turns a PostgreSQL `COUNT` or an `AVG` into a number with its decimals, and a `boolean` reads `0` / `'0'` as false on every database. A numeric SQL type converts the same way: `@CalculatedColumn('integer')`, `'bigint'`, `'numeric'`, `'decimal'`, `'float'`; a `transformer` replaces the conversion and gets the value as the database returned it. Unlike TypeORM's `@VirtualColumn`, it costs nothing until a query asks for it. It is a TypeORM virtual property, with their limits in older TypeORM versions: schema sync before 0.3.29 keeps the removed columns of its table, and `upsert` on TypeORM 0.3 fails with the property set; the docs list them.
- **`orderByTyped` / `addOrderByTyped` on a `@CalculatedColumn`**: order by the value of one selected with `addSelectCalculated`, also with `take` / `skip` and joins (they threw a `TypeError` for it in rc.9), and so does `applyOrder` for a `field` that is one, so a client can sort by it like by any column. The value is selected a second time under a generated `calculated_…` alias, which PostgreSQL and the DISTINCT query of a paged join can order by; ordering by it again reuses the alias. `distinctOnTyped` takes such a property too, under the same alias, so DISTINCT ON matches the leading ORDER BY as PostgreSQL requires: `.orderByTyped((user) => user.imagesCount, 'DESC').distinctOnTyped((user) => user.imagesCount)`.
- **`addSelectCalculatedTyped`**: `addSelectCalculated` with the property picked by a typed callback, `(user) => user.imagesCount`, or `(q) => q.owner.imagesCount` for the entity of a joined alias, which the callback names. The callback starts at the root set with `typed<Root>()`, else at the entity, so the property of a joined entity is checked at compile time too, where the string form takes any name. That it is a `@CalculatedColumn` is checked when the query is built, as for the string form. `orderByTyped` / `addOrderByTyped` order by it; the `orderByCalculatedTyped` / `addOrderByCalculatedTyped` of rc.9 are removed in their favour.
- **`tableHelper` `isIn`, `isNotIn`, `isAny` and `isNotAny`**: the conditions of `whereIsIn` / `whereIsNotIn` / `whereIsAny` / `whereIsNotAny` as strings, for a join condition, a `CASE`, a `filter` of `count` or a raw query: `t.isIn('id', ids, 'ids')` is `"user"."id" IN (:...ids)`, `t.isAny('id', ids, 'ids', 'uuid[]')` is `"user"."id" = ANY(CAST(:ids AS uuid[]))`. The values are read only to see whether there are any: without values the condition is `FALSE`, `TRUE` for the `Not` forms. The caller binds the values under the parameter name it passes, which may hold letters, digits and `_`; the array type is checked like that of `whereIsAny`.
- **`tableHelper(Entity, alias?, options?)`**: given the entity class instead of a type argument, the helper takes the type from it and writes the database column of each property: `tableHelper(User, 'user').adminEmail` is `"user"."email"` for `@Column({ name: 'email' }) adminEmail`, in `column()`, the column properties and every method built on them. The names come from the `name` of the column decorators on the class and its parents (the nearest wins), read once per class from TypeORM's metadata storage, so no `DataSource` is needed. Other columns keep their property names, as under the default naming strategy; a custom naming strategy and embedded columns are not applied. `tableHelper<Entity>(alias)` is unchanged.
- **Columns as properties of `tableHelper`**: `t.email` gives what `t.column('email')` gives, with the same alias and options, for each key of the entity or row type (`tableHelper<Record<'utm_id' | 'total', unknown>>('cte').utm_id` is `"cte"."utm_id"`); an unknown name doesn't compile. The members of the helper win: a column named `alias`, `count`, `where`, … is reachable through `column()` only. Symbols and the keys that JavaScript and test tools read on any object (`then`, `toJSON`, `inspect`, `asymmetricMatch`, `$$typeof`, `nodeType`, the members of `Object.prototype`) aren't columns, so `await`, `JSON.stringify`, `String()`, `util.inspect` and Jest matchers treat the helper as a plain object. The helper is a `Proxy` around the object it was, and its type is exported as `TableHelper<Entity>`.
- **`queryReturning` on `DataSource`, `EntityManager` and `Repository`**: runs a raw statement and resolves `{ records, affected }`, the same shape for every statement and driver. `query()` shapes its result by the command: on PostgreSQL an UPDATE or a DELETE resolves to `[rows, rowCount]` while a SELECT or an INSERT resolves to the rows, so taking the first element of an UPDATE … RETURNING yields the rows array instead of a row. On a manager bound to a query runner the statement runs on it, inside its transaction. On TypeORM 0.3's sqlite3 driver, whose runner reads no rows from an INSERT, UPDATE or DELETE, the `RETURNING` rows are read too.
- **`enableReservedQualifierGuard` / `disableReservedQualifierGuard`**: an opt-in check of the SQL every query builder runs on PostgreSQL and CockroachDB, for a reserved word used as a qualifier without quotes: `order."userId"`, `user.id`, `COALESCE(user."featureFlags" ->> 'x', '')`. TypeORM quotes the aliases it writes and maps `alias.property` only for an alias with an entity and an unquoted property, so such a word comes from SQL written by hand, which PostgreSQL rejects (`syntax error at or near "order"`; `user` is the `USER` key word). The check sits in `getQueryAndParameters()`, which every query passes before it runs (`getMany`, `getRawMany`, `getOne`, `getCount`, `stream`, `execute()` of insert, update, delete, soft delete and restore queries, and `getSql()`). In `'throw'` mode, the default, the query throws or rejects with a `ReservedQualifierError` that names the word, shows the SQL around it and the quoted reference; in `'warn'` mode it runs, and the error goes to `onViolation`, `console.warn` by default. Words in string literals (`E'…'` and dollar-quoted ones too), quoted identifiers, comments and parameters are skipped. The words are PostgreSQL's reserved key words (`POSTGRES_RESERVED_KEY_WORDS`; CockroachDB's on CockroachDB), which `words` replaces. Off until enabled: nothing is patched before the first call, and other databases aren't checked. `findBareReservedQualifiers(sql, words?)` is the check on its own; all of them are exported from `typeorm-extensions/helpers` too.
- **`valuesFromSelectTyped`**: an INSERT takes its rows from a select query, `INSERT INTO … (columns) SELECT …`, in place of `values()`. `columns` maps each property to the SQL its rows get, over the select's aliases; TypeORM still writes the table, the column list, `orIgnore`, `onConflictTyped` and `returning`, and only `VALUES (…)` is replaced. The select's selections follow TypeORM's column order and its parameters are renamed unique. Listeners and subscribers don't run, as there is no entity. PostgreSQL, MySQL and SQLite. TypeORM 1.x has a `valuesFromSelect` of its own, which takes the columns by position from `into()`; this one keeps another name and never replaces it (rc.6 named it `valuesFromSelect` and did). On SQLite a select without a WHERE gets `WHERE 1 = 1`, so an `ON CONFLICT` after it isn't read as a join constraint. Its wrappers are installed once per process, so two copies of the library in one project work together.
- **`SubQuery` / `SubQueryFactory`**: the type of a subquery argument, a query builder or a factory that builds it on the outer query's connection and transaction, as the EXISTS methods, `leftJoinLateral` / `innerJoinLateral` (also raw SQL there), `addSelectCalculated` (the factory) and `valuesFromSelectTyped` take it.
- **`onConflictTyped`**: `ON CONFLICT` on an INSERT with typed columns, on PostgreSQL and SQLite: `target` (properties of the unique index), `targetWhere` (a partial index's predicate), `set` (an object of properties and SQL, from `excluded` and `current`) and `where`; without `set` it is `DO NOTHING`. It also works on TypeORM 1.x, which dropped `onConflict()`.
- **`selectExpression(sql)`** in `typeorm-extensions/helpers`: orders by an SQL expression in `orderByTyped` / `addOrderByTyped`, and puts it into `distinctOnTyped`, without a property on the entity to select it into. It is selected once under a generated alias, like a `@CalculatedColumn` that is ordered by, and `getMany` leaves it out of the entities.
- **`selectRow(table, columns)`** and **`unnestRows(table, arrays)`**: the body of a CTE or subquery, checked against the row type of the `tableHelper` that reads it (`tableHelper<Record<'userId' | 'visits', unknown>>('visits')`), so a missing, extra or misspelled column fails type-check where the CTE is built as well as where it is read. `selectRow` replaces the selection with `<sql> AS "<column>"` per column, in the order given; `unnestRows`, in `typeorm-extensions/helpers`, returns `SELECT * FROM unnest(<array>, …) AS t("<column>", …)`, with `{ ordinality: 'ord' }` for `WITH ORDINALITY` (PostgreSQL). A `TableHelper<T>` carries `T` as `TableRow<T>`, type only.
- **TypeORM find operators in `whereTyped`**, `andWhereTyped` and `orWhereTyped`: the condition may be `IsNull()`, `Not(IsNull())`, `Equal(v)`, `In([…])`, `MoreThanOrEqual(v)`, `ILike(v)`, `Raw(…)` instead of SQL, rendered as `find({ where })` renders it, its values bound as parameters under unique names (`:op_…`): TypeORM's own `orm_param_N` restart at 0 in every builder, so a query that took the parameters of a subquery built on its own overwrote one value with the other. The value of a typed operator (`Equal`, `Not`, `MoreThan…`, `LessThan…`, `Between`, `Like`, `ILike`, `Any`) is checked against the column's type without `strictParams`, so `Equal('successful')` on an enum column fails type-check; TypeORM types `In()`, `IsNull()` and `Raw()` as `FindOperator<any>`, so **`IsIn([…])`** is `In` with its values typed, negated by `Not(IsIn([…]))`. **`IsTrue()`** / **`IsFalse()`** are `IS TRUE` / `IS FALSE` on a boolean column; never NULL, so `Not(IsTrue())` is `IS NOT TRUE` and matches NULL, unlike `Not(Equal(true))`. **`EqualColumn(sql)`** compares the column with another column or expression: `whereTyped((o) => o.userId, EqualColumn(users.id))`. **`IsDistinctFrom(value)`** is `IS DISTINCT FROM`, which matches a NULL column too; `Not(IsDistinctFrom(value))` is an `=` that matches NULL to NULL, and the value may be `null` (PostgreSQL, SQLite 3.39+). TypeORM's `Any([…])` binds a long list as one array parameter, `= ANY(:param)`, checked like `IsIn`.
- **`Sql`**, SQL functions and keywords as helpers: aggregates `count`, `sum`, `min`, `max`, `avg`, `boolOr`, `boolAnd`, `stringAgg` (with `distinct` and `filter`; `sum`, `min`, `max` and `avg` also with `else`, `SUM(CASE WHEN filter THEN x ELSE 0 END)`), `arrayAgg`, `jsonAgg`, `jsonbAgg` (with `distinct`, `orderBy` and `filter`); `coalesce`, `nullif`, `greatest`, `least`, `case` and `caseOf` (`{ when, then }` branches and `{ else }`); `lower`, `upper`, `trim`, `length`, `concat`, `substring`, `splitPart`, `cast`; `round`, `abs`, `floor`, `ceil`; `now`, `interval`, `addInterval`, `ago`, `extract`, `toChar`, `atTimeZone`, `dateTrunc`; `json` / `jsonText` (a value at a JSON path: `->` / `->>`, `JSON_EXTRACT` on MySQL), `jsonBuildObject`, `jsonbBuildObject`; window functions `rowNumber`, `rank`, `denseRank`, `lag`, `lead`, `firstValue`, `lastValue` and `over` (with `partitionBy`, `orderBy` and a `frame`); `distinctOn`; `jsonbSet`, `toJsonb`, `jsonbTypeof`, `jsonbArrayElements`, `jsonbArrayElementsText`, `jsonbArrayLength`; `arrayPosition`; `regexpReplace`; `isDistinctFrom`, `isNotDistinctFrom` (MySQL `<=>`, SQLite `IS [NOT]`); `similarity`, `wordSimilarity`, `strictWordSimilarity` (pg_trgm); `llToEarth`, `earthDistance`, `earthBox` (earthdistance). They take SQL expressions, such as the columns of a `tableHelper` (`Sql.max(t.createdAt)` is `MAX("t"."createdAt")`), and write the function as it is: `Sql.count` and `Sql.sum` don't cast or replace NULL like `tableHelper`'s `count` and `sum`, so they replace a hand-written `COUNT(…)` / `SUM(…)` without changing the result. Where databases differ `Sql` writes PostgreSQL, and **`Sql.for(driver)`** the given database: `Sql.for('mysql').length(x)` is `CHAR_LENGTH(x)`, `Sql.for('sqlite').ago(30, 'days')` is `datetime('now', '-30 days')`; a function the database has no form of throws a `TypeError`. Amounts, units, date parts, separators, formats and JSON keys are checked or written as SQL strings; a missing expression and a `cast` type that isn't a type name throw a `TypeError`. Where a function takes a value (`coalesce`, `nullif`, `greatest`, `least`, `concat`, `case` values, the aggregates, `round`, `abs`, `floor`, `ceil`, `cast`, the default of `lag` / `lead`, the values of `jsonBuildObject`), a number goes too, written as a literal (`SqlValue`): `Sql.coalesce(Sql.sum(t.total), 0)` is `COALESCE(SUM("t"."total"), 0)`; `NaN` and infinities throw a `TypeError`. `percentileCont`, `percentileDisc` and `mode` (`WITHIN GROUP (ORDER BY …)`) and `jsonbMerge` (`COALESCE(target, CAST('{}' AS jsonb)) || patch`), PostgreSQL; an interval amount may be an SQL expression, `{ sql: ':days' }` (`make_interval(days => :days)` on PostgreSQL); `Sql.for(driver, { syntax: 'filter' })` writes the aggregates' `filter` as `FILTER (WHERE …)` by default; `Sql.count({ filter })` counts the matching rows.

### Improvements

- **`WhereInMethods` / `WhereAnyMethods` are deprecated** in favour of `WhereIsInMethodName` / `WhereIsAnyMethodName`, as `WhereIsInMethods` / `WhereIsAnyMethods` are the interfaces of the methods themselves. The old names stay as aliases.
- **Licensed under MIT, and the package ships the license text**: `package.json` said ISC, but there was no `LICENSE` file in the repository or the npm package. From 3.0.0 on the license is MIT, with the text in `LICENSE`; versions up to 2.1.0 stay ISC.
- **`whereIsIn` / `whereIsAny` and their variants return `this` on every builder**: on update, delete and soft delete builders they were declared to return `UpdateQueryBuilder<Entity>` and the like, which dropped the mark of `typed<Root>()`; they are declared once now, as the other where methods are (`WhereIsInMethods`, `WhereIsAnyMethods`).
- **`getManyWithTotals` runs its count and its page query at the same time**, so the call takes as long as the slower one instead of their sum. The count goes on a clone of the builder, taken before the page query applies its limit. On a builder bound to a query runner — from a transactional manager, or inside `dataSource.transaction` — the two still run one after another: there is a single connection, on which the driver would serialise them anyway.
- **`tableHelper` takes a `driver` option**: `tableHelper('user', { driver: 'mysql' })` quotes with backticks.
- **`selectTyped` / `addSelectTyped` take `useQuotes` right after a callback**: `selectTyped(user => [user.id, user.name], true)`, as an array of callbacks already did. The second argument after a callback was typed as the alias only, so quoting a callback that selects several fields needed `selectTyped(cb, undefined, true)`. A string there is still the alias. Types only: the method already read a boolean in that place.
- **`whereSearchTyped` and its variants take one callback selecting the columns**: `andWhereSearchTyped(user => [user.firstName, user.email], search)`, the same SQL as `[user => user.firstName, user => user.email]`. A raw `{ sql }` expression still goes in the array form. A callback that selects no column throws, as an empty array does.

### Bug Fixes

- **The `Sql` helpers take the columns of `onConflictTyped` and `returningTyped`**: those columns are typed as strings and become SQL only when read as one, so `Sql.coalesce(excluded.name, current.name)` type-checked and threw `TypeError: Sql.coalesce(): the argument is an SQL expression` when the query was built. Every `Sql` argument that takes an expression now takes such a column, alone or in a list.
- **The parameters of a builder CTE under `take` / `skip`** (TypeORM's own, new module `common-table-expression.extension`): TypeORM hands them to the query only while it writes the WITH clause, and the DISTINCT id query of `getMany` / `getOne` with `take` or `skip` and a join writes it on a clone, then binds the original's parameters, so the query failed on the CTE's placeholder. `getParameters()` now includes the parameters of every builder CTE, over the query's own as the WITH clause sets them.
- **`whereSimilarTyped` on a path into a JSON column**: `%` binds tighter than `->>`, so `"a"."meta" -> 'author' ->> 'name' % :t` read as `… ->> ('name' % :t)` and failed with `operator does not exist: jsonb ->> boolean`. A key that isn't a plain column is put in parentheses before a trigram operator; plain columns keep their SQL.
- **`getRawManyWithCursor` with a key whose SQL holds a generated parameter name**: the cursor names its keys by a hash of their SQL, and a name like `:similarity_ab12c` changes on every request, so the second page threw `InvalidCursorError`. The query's parameter names are left out of the hash now. Keys without parameters keep the names their cursors carry; a cursor of an earlier release candidate for a key with a parameter is refused once.
- **The conditions that narrow a query respect an OR written in one `where`**: `applyPeriodFilter`, the cursor of `getManyWithCursor` / `getRawManyWithCursor`, the correlation of `where…RelationExists` and the empty-list `FALSE` of `innerJoinUnnest` put the existing conditions in parentheses only after `orWhere`. `where('a OR b')` is one condition to TypeORM, written without them, so `a OR b AND c` ran as `a OR (b AND c)`: a period filter on a DELETE deleted rows outside the period, a cursor walk returned its first page forever, and a relation-exists callback with an OR bypassed the correlation. Existing conditions that may hold an OR (an `orWhere`, or `OR` / `||` in a string) are now wrapped; a plain AND chain is written as before.
- **`addSelectCalculated` with a subquery factory keeps its parameters apart**: the factory ran on TypeORM's `subQuery()`, which sets its parameters on the outer query under their own names, so two factories binding `:status` both read the last value and returned wrong counts without an error. The factory now runs on a detached builder and its parameters are renamed, as in `leftJoinLateral` and `fromUnion`.
- **A typed key named like a method of the key holder**: `whereTyped(p => p.push, …)` returned `KeyHolder.push` instead of the key and threw `keyHolder.getKeys is not a function`; so did `unshift`, `_keys` and the members of `Object.prototype` (`constructor`, `hasOwnProperty`, …). Only `getKeys`, `toSql`, `toString` and `valueOf` are read from the holder now; every other name is a key.
- **`getManyWithCursor` on a table whose primary key holds a date**: the key was read as text for the cursor and then compared with the entity's `Date` to find the last row of the page, which never matched (`could not find the key values of the last row`), e.g. on a partitioned table whose key includes the partition timestamp. Such a key is also read as is for that comparison.
- **A cursor made for the opposite direction is refused**: it named its keys without their direction, so a cursor from `id DESC` read as a position in `id ASC` and returned a wrong page. Keys in `DESC` are now written `-id` (`-sql:…` for a raw key): ascending cursors are unchanged, and a descending cursor made by an earlier version throws `InvalidCursorError` once.
- **A page past the last offset is an empty page**: `page: '1e21'` was written as `OFFSET 1e+22`, which every database rejects. `page` and `pageSize` are capped so the offset stays within `Number.MAX_SAFE_INTEGER`.
- **`whereNotExists` / `where…RelationExists` with a HAVING on a select alias**: the subquery's select list was replaced with `1`, so `having('cnt > 1')` failed on MySQL and SQLite (`no such column: cnt`). With a HAVING, the aliased selections stay; an entity's own columns are still dropped.
- **`getRawManyWithTotals` on MySQL with two columns of one name**: the count wraps the query in a derived table, which MySQL refuses with duplicate column names (`SELECT *` over a join). Without DISTINCT, GROUP BY or HAVING the count now reads `SELECT 1` there.
- **`fromUnion` / `addCommonTableExpressionUnion` on SQLite with a CTE in a later part**: only parts with ORDER BY or LIMIT became subqueries, and SQLite rejects a `WITH` after the first part. A part with a common table expression is wrapped too.
- **A JSON path compared by order with numeric text compares numbers**: `whereTyped(a => a.meta.score, '>=', '10')`, the value as a query string gives it, compared the path as text on PostgreSQL (`'9' >= '10'` is true) and a JSON number with text on SQLite (always less), so it matched the wrong rows without an error. With `<`, `>`, `<=` and `>=` a string that is a number is now bound as that number. Other operators keep strings as text.
- **An order field or table alias can't carry SQL**: `applyOrder` / `applyOrderFilter` quote `field` and `tableAlias` as one identifier, but a value that started and ended with a quote passed as already quoted, so `"id" * (SELECT …), "id"` reached the ORDER BY as written and an order taken from a request could run a subquery. Only one whole quoted identifier is kept now (`"first name"`, `"a""b"`); anything else is quoted as one name, and the database rejects the unknown column. `tableHelper().column()` and the quoting built on it got the same fix. With `useQuotes: false`, where the field and the alias reach the SQL as written, anything but column names (`createdAt`, `user.createdAt`) throws a `TypeError`. A segment quoted for another database is unquoted and quoted again in the database's own quotes: MySQL reads `"…"` as a string literal with backslash escapes, so `"\"." OR SLEEP(5) -- "` as a `tableAlias` reached it as SQL.
- **A typed key that isn't a property can't close its identifier**: `orderByTyped(u => u[sort])` or `whereTyped(u => u[key], …)` with the key from a request wrapped it in quotes without doubling a quote inside it, or passed it on unquoted. A key holding a quote character is now quoted with it doubled, and one that isn't a plain name is quoted.
- **Array conditions outside PostgreSQL**: `whereArrayOverlaps` wrote `&&`, which MySQL reads as a logical AND, and returned the wrong rows; `@>` and `<@` were syntax errors. `whereArrayContains`, `whereArrayContainedBy` and `whereArrayOverlaps` throw a `TypeError` on other databases.
- **`applyOrder` with `take` / `skip` and joins**: an order with an alias (`{ alias: 'user' }`, `tableAlias`, or the main alias for `id`, `createdAt`, …) was written `"user"."first_name"`, and the DISTINCT query TypeORM builds for take with joins threw `"user" alias was not found`. An entity property under an alias with an entity is now written `user.firstName`, which TypeORM maps to the same column. `useQuotes: true` given explicitly still quotes.
- **`nulls` on MySQL / MariaDB**: they have no `NULLS FIRST` / `NULLS LAST`, and the query failed with a syntax error. The order is emulated there: `(column) IS NULL` is selected under a generated `nulls_…` alias and ordered by first, so it works with take and joins too. Raw rows (`getRawMany`) carry that column.
- **`isReversed` as `1` / `0`**: it was ignored, while `direction` reads `1` / `-1`. `1` and `'1'` reverse the order, `0` and `'0'` don't.
- **Order and pagination filters of another shape**: `applyOrderFilter` takes one order given as an object, as a query string parses `?orderBy[field]=id`; it threw `orderBy.reduce is not a function`. An order without a string `field` throws a `TypeError` that says so. `getManyWithTotals`, `getRawManyWithTotals` and `applyPagination` read a missing pagination filter as the first page; they threw `Cannot destructure property 'page'`.
- **`whereIsIn` / `whereIsAny` / `innerJoinUnnest` given one value or an object**: a number (`@Type(() => Number)` on `?excludeIds=2`) or the object a query string makes of a long list (`{ 0: '1', 1: '2' }`) has no length, so IN matched no row and NOT IN every row, without an error; one string (`?ids=2`) made invalid SQL. One value is now a list of one, an object with array-index keys is the list of its values, `''` stays an empty list, and anything else throws a `TypeError`. The typed variants too.
- **A cursor edited by a client gives an `InvalidCursorError`**: `getManyWithCursor` checked a cursor's shape and keys but not its values, so `"abc"` for an integer key failed in the database (`invalid input syntax for type integer`, a 500 where the client sent a bad cursor) and matched nothing on SQLite. A value of a numeric, uuid, date / time or boolean key that doesn't fit the column is rejected now.
- **`applyPeriodFilter` with ISO strings on SQLite**: SQLite keeps a datetime as text, `2024-01-31 10:00:00.000`, and compared it with `2024-01-31T09:00:00.000Z` as text, by the `T`: a `periodFrom` later the same day matched nothing. A string with a time and an offset is now bound as a `Date`, which TypeORM writes in the stored form. Strings without an offset, and other databases, are as before.
- **`applyOrder` / `applyOrderFilter` read `isReversed` and `direction` from query-string text**: an unparsed query parameter holds `'true'` / `'false'` and `'-1'`, and `isReversed: 'true'` ordered ascending, because only a boolean was read. They are now read like the boolean and number they stand for. A `direction` that isn't one of the accepted values (`'ascending'`) is `ASC`; before, anything containing `asc` or `desc` went to TypeORM upper-cased, and TypeORM threw.
- **`applyOrder` / `applyOrderFilter` take `nulls` in the SQL form too**: `nulls: 'NULLS LAST'` became `NULLS NULLS LAST`, which TypeORM rejects. `first` / `last` and `NULLS FIRST` / `NULLS LAST` are read in any case and with spaces around, and `NullsOrder` admits the SQL form. Any other value now adds no `NULLS`: before, anything containing `first` or `last` produced invalid SQL (`'firstly'` → `NULLS FIRSTLY`).
- **`leftJoinTyped` and the other typed joins given a string join it**: from untyped code, a string in place of the callback added no join and returned the builder as it was. It is joined as written now, as the typed map joins already did.
- **A `KeyHolder` in `selectTyped`, `orderByTyped` and `addOrderByTyped` is read like a callback**: a single one wrote its keys without the main alias and, with `useQuotes`, the property name instead of the column of a renamed `@Column({ name })`; in an array it got the alias but still the property name. Both now go through the key resolution of the callbacks: the main alias, the database column when quoted, an alias added later resolved when the SQL is built, and a key deeper than `alias.column` throws a `TypeError` instead of being cut to two levels.
- **A params object whose value goes after the condition takes one key**: `whereTyped(u => u.id, '=', { id: 1, email })` used the first value and dropped the others without a word, and `{}` compared the column with `NULL`. Both now throw a `TypeError`. Objects whose keys the condition names (`'BETWEEN :from AND :to'`) and `addValue: false` are as before.
- **Identifiers quoted for MySQL / MariaDB**: `applyOrder` / `applyOrderFilter`, and `orderByTyped` / `addOrderByTyped` / `selectTyped` with `useQuotes`, put double quotes around column names on every database. On MySQL a double-quoted name is a string, so ordering by `"ticket_status"` ordered by a constant and returned the rows in no particular order without an error, and `"t"."ticket_id"` was a syntax error. They now quote with backticks there. The test suite runs on MySQL 8.4 in CI.
- **`getManyWithTotals` with a cache id read the count and the page from one cache entry**: with `.cache('id', ms)` the count ran under the page query's id, so every call after the first got the other query's cached rows: an empty `list`. The count is now cached under `<id>-count`, as TypeORM's `getManyAndCount` does; `getRawManyWithTotals` does the same, and its default count subquery is cached too.
- **`getManyWithTotals` no longer returns with a query in flight when the other one fails**: with the count and the page running at the same time, `Promise.all` rejected as soon as one failed, while the other kept running on its pooled connection and its outcome was dropped. The call now waits for both and then rejects with the first error, the count's if both failed. A page that fails before its query starts, on a limit TypeORM rejects, waits for the count too.
- **`whereArrayContainsTyped` / `ContainedByTyped` / `OverlapsTyped` on an array inside a JSON column**: the path was read as text and compared with an array operator, an error in the database. It is now compared with jsonb operators: `@>` and `<@` against the values as a JSON array, and `?|` for an overlap of strings, on arrays only: a string or an object at the path doesn't match.
- **`orderByArrayPositionTyped` on a value inside a JSON column** compared the value as text: a stored `3.0` didn't match `3`, and with `arrayType: 'int[]'` the query failed. The value is now cast to the type of the values, as typed where methods do; a value of another JSON type goes last instead of failing the cast.
- **`tableHelper.count()` on MySQL**: `CAST(COUNT(…) AS integer)` is a syntax error there. With `driver: 'mysql'` it casts `AS SIGNED`.
- **Column names inside `Brackets` and subqueries**: the builder TypeORM passes to a `Brackets` callback has the outer query's main alias but none of its aliases, so typed keys there kept the property name: `where.whereTyped((o) => o.calculatedAmount, …)` gave `"o"."calculatedAmount"` instead of the `@Column({ name: 'calculated_amount' })` column, an error in the database; the same for a joined alias (`j.u.fullName`) and for string fields (`whereIsIn('u.fullName', …)`). In a subquery, an alias of the outer query had the same problem. Aliases are now looked up in the queries the builder is part of too.
- **Typed select / order / group by / distinct on an alias without metadata**: without `useQuotes`, `orderByTyped` / `addOrderByTyped`, `selectTyped` / `addSelectTyped`, `groupByTyped` / `addGroupByTyped` and `distinctOnTyped` gave `alias.property` for every alias. TypeORM maps that to the column only for an alias with metadata; for a subquery or a table in FROM or a join that isn't an entity (`.from('recent_events', 'recentEvents')`) it stays as written, and PostgreSQL folds the unquoted `recentEvents.startsAt` to `recentevents.startsat`: `missing FROM-clause entry for table "recentevents"`. Keys of such an alias are now quoted, as typed where methods already did, also when the alias is added after the call (`.selectTyped(…).from(subQuery, 'pairs')`) or never: an alias that only raw SQL adds, such as a `LATERAL` subquery in the condition of a raw join, is quoted when the SQL is built. `useQuotes: false` keeps them unquoted in the methods that take it. A column that raw SQL names without quotes (`SELECT id AS userId`) is `userid` on PostgreSQL, so a camelCase key for it (`cte.userId`), which used to match after folding, now doesn't: quote the column name in the SQL (`AS "userId"`), or pass `useQuotes: false`.
- **Typed keys on an alias added after the call**: typed where methods, and select / order / group by with `useQuotes`, mapped the property to its column through the aliases the query had when the method was called. Before the join that adds the alias, `whereTyped((j) => j.usr.receiptsEmail, …)` kept the property name, `"usr"."receiptsEmail"`, instead of the `@Column({ name: 'receipts_email' })` column; the same for string fields (`whereIsIn('usr.receiptsEmail', …)`). Such keys are now resolved when TypeORM builds the SQL, as it does for unquoted keys. An alias that is still unknown then, or has no metadata, keeps the property name as before.
- **Typed select / order / group by / distinct on a relation without a join column or an embedded entity** (`user => user.images`, `person => person.address`) built SQL the database rejects. They now throw a `TypeError`. A many-to-one relation still selects its join column.
- **A typed where with an `undefined` value after an operator**: `whereTyped((u) => u.email, '=', undefined)` gave `"user"."email" =`, a syntax error in the database. It now throws a `TypeError` that names the condition. A condition that ends with a parameter set later (`'ILIKE :like'` with `setParameter`) is unaffected, and `null` and `{ email: undefined }` compare with `NULL`, as before.
- **Where methods on soft delete and restore queries**: `whereIsIn`, `whereIsAny`, `whereArrayContains`, `whereJsonContains`, `whereIsDistinctFrom`, `applyPeriodFilter`, their `and…` / `or…` / `…Not…` forms and their typed variants (`whereTyped`, `whereIsAnyTyped`, `whereILikeTyped`, …) were added to select, update and delete queries only: `createQueryBuilder().softDelete().whereIsAnyTyped(…)` threw `… is not a function`. They are now on `SoftDeleteQueryBuilder` too, which `softDelete()` and `restore()` return, with the SQL they give on an update.
- **A query builder of an entity didn't compile as a `SelectQueryBuilder<ObjectLiteral>` under the root import**: `getManyWithCursor`, which `import 'typeorm-extensions'` loads, took the entity's property names in its `options`, which made the builder invariant in its entity: a `SelectQueryBuilder<User>`, and the builder `typed()` returns, was no `SelectQueryBuilder<ObjectLiteral>` argument (TS2345), and didn't cast to the builder of rows it has the columns of (`as SelectQueryBuilder<{ email: string }>`, TS2352). `getManyWithCursor` is now generic over the entity of the builder it is called on, which it infers: `orderBy` still takes that entity's properties, and `list` is still its entities.

## [2.1.0] - 2026-11-09

A minor version: nothing needs changing when upgrading from 2.0.0. `strictParams` is opt-in, and a typed key
into a JSON column used to build SQL that failed, so no working query changes.

### New Features

- **`strictParams`: typed where parameters checked against the column type**, opt-in through module augmentation:
  ```ts
  declare module 'typeorm-extensions' {
    interface TypeormExtensionsConfig {
      strictParams: true;
    }
  }
  ```
  The type of the column comes from the callback, the expected value from the operator of `whereTyped` / `andWhereTyped` / `orWhereTyped`:
  - `=`, `<>`, `!=`, `<`, `<=`, `>`, `>=` take the column's value, never `null` / `undefined` (`= NULL` matches no row); `IS [NOT] DISTINCT FROM` takes `null` too, `IS` / `IS NOT` only `null`;
  - `IN` / `NOT IN` take an array of values, `LIKE` / `ILIKE` (and `NOT`) a string, `IS NULL`, `IS TRUE` and the like nothing;
  - a date column takes a `Date` or a string; the value may be passed as is or in a `{ name: value }` params object, except a plain object (a JSON column), which only fits in a params object: at runtime a plain object always is one.

  `whereIsInTyped` / `whereIsAnyTyped` and their `Not`, `and` / `or` variants take an array of the column's values. Conditions written as SQL (`'BETWEEN :from AND :to'`, `'= true'`) and calls with an explicit type argument (`whereTyped<Joins>(…)`) stay unchecked. Without the option nothing changes.

- **Typed keys into JSON columns**: in typed where methods a callback may go into a `json` / `jsonb` / `simple-json` column, `exec => exec.details.meta.endTs` → `"exec"."details" -> 'meta' ->> 'endTs'`, on the main entity or a joined alias. On PostgreSQL the path is cast to the type of the compared value (`numeric`, `boolean`, `timestamptz`), since `->>` gives text and text compares `'9' >= '10'` as true; `whereJsonContainsTyped` / `whereJsonHasKeyTyped` take the JSON value (`->`). PostgreSQL and SQLite 3.38+, other databases throw a `TypeError`.
  - Two levels work with any JSON column. For deeper paths mark the property with the new `Json<T>` type (`details: Json<ExecutionDetails>`): TypeScript can't tell a JSON object from a relation, and relations still stop at `alias.column`.
  - Select, order and distinct take columns only: a JSON path there throws a `TypeError`.
  - `applyPeriodFilterTyped` compares a JSON path as a timestamp: `CAST(… AS timestamptz)` on PostgreSQL, `strftime` on SQLite. As text, a date stored as `'…T12:00:00.000Z'` didn't match a `Date` bound on its own day.

### Bug Fixes

- **A typed key into a JSON column built a wrong column**: `u => u.metadata.role` gave `"metadata"."role"`, as if `metadata` were an alias, which failed in the database. Where methods now build the JSON path, select / order / distinct throw a `TypeError`.
- **Typed callbacks give a `Date` (or `Buffer`) column its own type**: the proxy used to treat it as an object to go into, so `u => u.createdAt` was typed as a mapped `Date`, and a date column of a relation (`u => u.images.createdAt`) as the end of the key path.

## [2.0.0] - 2026-11-05

A major version: the changes under **Breaking Changes** need code changes when upgrading from 1.x
(`^1.3.5` ranges don't pick 2.0.0 up). Most of the **Bug Fixes** make SQL correct that used to fail,
e.g. typed keys and `applyOrder` now use database column names (`@Column({ name })`).

### Breaking Changes

- **Renamed `useDoubleQuotes` to `useQuotes`** in `ApplyOrderOptions`. The positional `useDoubleQuotes` parameter of `selectTyped` / `addSelectTyped` is renamed to `useQuotes` as well (positional calls keep working).
- **Removed `useDoubleQuotes` from the typed where options** (#29):
  - `TypedWhereOptions` (`whereTyped` and its `and` / `or` variants) keeps only `addValue`;
  - `whereIsInTyped` / `whereIsNotInTyped` and their `and` / `or` variants no longer take an options argument, and the exported `TypedWhereIsInOptions` type is removed.

  The option never had an effect, in 1.3.5 either: the key was quoted with or without it, and typed keys are now always the quoted database column. Migrate by deleting `useDoubleQuotes` from `whereTyped` options and dropping the last argument of `whereIsInTyped` calls.
- **`whereTyped` / `whereIsInTyped` / `whereIsNotInTyped` (and their `and` / `or` variants) throw a `TypeError` for a callback that selects several columns,** like `whereIsAnyTyped` (#29).
  - Previously they added one condition per column: `where…` kept only the last one, while `and…` / `or…` silently joined them with AND / OR.
  - Migrate to one call per column. For an OR search over several columns, use `whereSearchTyped`.
- **`addOrderByTyped` takes an options object as its 4th argument**: `useDoubleQuotes?: boolean` became `options?: TypedOrderByOptions`. Migrate `addOrderByTyped(cb, 'ASC', undefined, true)` to `addOrderByTyped(cb, 'ASC', undefined, { useQuotes: true })`. In plain JS a boolean passed there is now ignored, so `true` silently stops quoting the key (`user.name` instead of `"user"."name"`).
- **Typed key paths are limited to `column` / `alias.column`** (#16). A callback reaching a third level (`u => u.images.user.email`, `u => u.metadata.settings.theme`) is a compile error and throws a `TypeError` at runtime. Previously the path was cut to its first two keys without notice: typed where failed in the database, while select / orderBy / distinctOn used the relation's join column, so `x => x.images.user.id` happened to return the foreign key and any other field returned it too. Migrate `x.rel.rel2.id` to the foreign key property (`x => x.images.userId`); for other columns of nested relations, join them and address the join alias with an alias-keyed type (`(j: { imageUser: UserEntity }) => j.imageUser.email`).
- **String fields that the query can't resolve are quoted only when they are paths of identifiers** (#14, #28): the untyped methods (`whereIsIn`, `whereIsAny`, …) quote a column of a query alias whatever its name (`'user.first-name'` → `"user"."first-name"`), and leave an expression such as `LOWER(u.email)` as it is. A field the query doesn't know (an alias of a subquery or of a table given by name) is quoted only when it is a path of plain identifiers: a name like `sub.first-name` there used to be quoted piece by piece and is now passed as is. Quote such a name yourself: `'sub."first-name"'`.
- **`ArgsType` is `readonly unknown[]`** (#11), so the IN / ANY methods accept readonly arrays. Code that used the exported `ArgsType` for its own arrays and changes them (`push`, assignment by index) needs `unknown[]` instead.

### New Features

- **TypeORM 1.x support**: the peer dependency is `"typeorm": "^0.3.12 || ^1.0.0"`, so the package installs next to TypeORM 1.x without `--legacy-peer-deps`. CI tests TypeORM 0.3.12, the latest 0.3.x and the latest 1.x; every release from 0.3.24 to 1.1.2 was tested on SQLite and PostgreSQL. (#30, #31)
- **`tableHelper` utility**, exported from the package root (`import { tableHelper } from 'typeorm-extensions'`) — type-safe SQL helper for building column references, WHERE expressions, JOIN clauses, and JSONB accessors. (#5)
  - `column()` — quoted SQL column identifier
  - `where()` — column with expression
  - `join()` / `joinOn()` — join path helpers (`join(relation, alias?)` throws when there is no alias; #29)
  - `isNull()` / `isNotNull()` — null check expressions
  - `count()` / `cast()` — aggregate and cast helpers (#7, #29). `count(column?, { distinct, filter, syntax })`:
    - `COUNT(*)` without a column;
    - `COUNT(DISTINCT col)` with `distinct`;
    - conditional counts with `filter`, as `COUNT(CASE WHEN … THEN … END)` by default (any database) or, with `syntax: 'filter'`, `COUNT(…) FILTER (WHERE …)` (PostgreSQL, SQLite 3.30+).
  - `jsonColumn()` — full JSONB column access expression with typed field names
  - `jsonPath()` — JSONB operator fragment for use in `whereTyped` conditions strings
- **JSONB access via `tableHelper`** with nested paths as rest params. Field names are inferred from the column's TypeScript type (autocomplete up to 4 levels deep) and escaped as SQL string literals (#8):
  ```ts
  const t = tableHelper<User>('user');
  t.jsonColumn('metadata', '->>', 'role')               // "user"."metadata" ->> 'role'
  t.jsonColumn('metadata', '->>', 'settings', 'theme')   // "user"."metadata" -> 'settings' ->> 'theme'
  t.jsonPath('metadata', '->>', 'role')                  // ->> 'role'
  ```
- **`TypedOrderByOptions`** — options for `orderByTyped` and `addOrderByTyped` with `useQuotes` support (`orderByTyped` had no quoting option before).
- **`whereIsAny` / `andWhereIsAny` / `orWhereIsAny`** and typed `whereIsAnyTyped` / `andWhereIsAnyTyped` / `orWhereIsAnyTyped` (PostgreSQL): `column = ANY(:array)` with the whole array bound as one parameter, so the number of values isn't limited by the 65535 bind parameters that `IN` runs into. An empty array becomes `FALSE`. (#12)
- **`typeorm-extensions/helpers`**: a side-effect-free entry point that exports `tableHelper` (and its types) without installing any QueryBuilder extension, unlike the package root. (#18)
- **`whereIsAny` `arrayType`** (+ typed): an optional third argument casts the array parameter, `= ANY(CAST(:param AS uuid[]))`; the type name is validated. **`whereIsNotAny`** / `andWhereIsNotAny` / `orWhereIsNotAny` (+ typed) build `<> ALL(:param)`: the column differs from every value; an empty array becomes `TRUE`, like `NOT IN`. (#19)
- **PostgreSQL array and JSON where methods** (+ `and` / `or` and typed variants, on Select, Update and Delete builders) (#21):
  - `whereArrayContains` / `whereArrayContainedBy` / `whereArrayOverlaps`: `@>`, `<@`, `&&` on array columns, the values bound as one array parameter, with an optional `arrayType` cast.
  - `whereJsonContains` / `whereJsonHasKey`: `@>` and `?` on the column cast to `jsonb`, so `json` and `simple-json` columns work too; on `jsonb` columns the cast is dropped and a GIN index is still used.
- **`whereIsDistinctFrom` / `whereIsNotDistinctFrom`** (+ `and` / `or` and typed variants): null-safe comparisons, where `NULL` equals `NULL`. `IS [NOT] DISTINCT FROM` on PostgreSQL and most databases, `<=>` on MySQL / MariaDB, `IS [NOT]` on SQLite. (#21)
- **String search methods** (typed, with `and` / `or` variants, on Select, Update and Delete builders) (#27):
  - `whereILikeTyped(sel, value, { match, escape, unaccent })`: `ILIKE` with `%` / `_` / `\` escaped and `contains` / `prefix` / `suffix` / `exact` matching (`LIKE` on MySQL / MariaDB, `LIKE … ESCAPE` on SQLite); a blank value adds nothing.
  - `whereSearchTyped([...selectors], value, options)`: one parenthesized `OR` group of `ILIKE`s over several columns or SQL expressions, with a single parameter.
  - `whereLowerEqualsTyped` / `whereIsInLowerTyped`: `LOWER(col) = LOWER(:p)` / `LOWER(col) IN (…)`, with a `normalize` wrapper to match an expression index.
  - `whereSimilarTyped` / `addSimilarityScoreTyped` (PostgreSQL + `pg_trgm`): `%`, `%>`, `<%` and `similarity()` scores.
  - `escapeLikePattern`, exported from the root and from `typeorm-extensions/helpers`.
- **`PeriodFilter` + `applyPeriodFilter` / `applyPeriodFilterTyped`** (Select, Update, Delete; any database): `{ periodFrom?, periodTo? }` of `Date | string` adds `column >= periodFrom` / `column <= periodTo` with AND around the existing conditions. Missing or empty ends are skipped; `includeFrom` / `includeTo: false` exclude an end; a date-only string is a whole day (`periodTo: '2024-01-31'` → `< '2024-02-01'`). (#23)
- **`getManyWithCursor(cursorFilter, { orderBy })`**: keyset (cursor) pagination returning `{ list, nextCursor }`. The primary key is appended to the order, date / time keys keep the database's precision (PostgreSQL microseconds), and an invalid cursor throws the exported `InvalidCursorError`. (#23)
- **`orderByArrayPosition` / `addOrderByArrayPosition`** (+ typed, PostgreSQL): order by the position of the column's value in an array, also with `take` and joins. (#23)
- **`returningTyped(x => [x.id, x.status])`** on Insert, Update, Delete and SoftDelete builders: RETURNING columns from entity properties, throwing for properties that aren't columns. (#23)

### Bug Fixes

- Typed proxy callbacks no longer fail with type errors on array relations (e.g. `user => user.images.url` where `images` is `ImageEntity[]`): arrays are unwrapped in the proxy type of all typed methods.
- `whereIsNotInTyped` / `andWhereIsNotInTyped` / `orWhereIsNotInTyped` on `SelectQueryBuilder`, `UpdateQueryBuilder` and `DeleteQueryBuilder` now default `Type` to the builder's entity, like the `IsIn` variants. Previously the callback accepted any property. (#4)
- `whereTyped` / `andWhereTyped` / `orWhereTyped`: when `options.addValue` is not set, it now defaults to `false` if `condition` already references a key of `params` (`'= :id'` with `{ id }`, `'IN (:...ids)'` with `{ ids }`). Previously a second placeholder was appended and the SQL was invalid. `::type` casts and colons inside literals are not treated as placeholders. (#6)
- `whereIsIn` / `whereIsNotIn` and their `and` / `or` and typed variants accept readonly arrays and `as const` constants: the values argument (`ArgsType`) is now `readonly unknown[]`. Previously they failed to type-check with TS2345. (#11)
- Fields of `whereIsIn` / `whereIsNotIn` / `whereIsAny` and of the typed where methods: only a path of identifiers is quoted (`user.id` → `"user"."id"`, `user.*` → `"user".*`); an expression such as `COALESCE(ts."instructorId", e."instructorId")`, `LOWER(u.email)` or `u.id::text` is used as is. Previously it was split on dots and quoted piece by piece into invalid SQL. See also Breaking Changes. (#14)
- Typed where methods on `UpdateQueryBuilder` / `DeleteQueryBuilder` no longer qualify the column with the alias: `WHERE "firstName" = …` instead of `WHERE "UserEntity"."firstName" = …`, which PostgreSQL accepted only when the alias equaled the table name and SQLite rejected. (#15)
- Typed where methods (`whereTyped`, `whereIsInTyped` / `whereIsNotInTyped`, `whereIsAnyTyped`) map properties to their database column names (`@Column({ name })`) through the alias metadata. Previously they emitted the property name, so a condition on a renamed column hit a nonexistent (or wrong) column. (#17)
- Typed keys on embedded columns (`p => p.address.city`) resolve to the main alias column (`"p"."addressCity"`) in where, select, orderBy and distinctOn, instead of being read as alias `address`. With `useQuotes`, `selectTyped` / `orderByTyped` emit database column names, and an array of callbacks in `selectTyped` honors `useQuotes`. (#20)
- `whereTyped` / `andWhereTyped` / `orWhereTyped` bind a `Date` (or a `Buffer` / typed array) as the value. Previously it was read as a params object: a `Date` has no own keys, so `whereTyped(u => u.createdAt, '>', date)` compared with `NULL` and returned nothing, and a `Buffer` was bound as its first byte. An invalid `Date` compares with `NULL`, like `NaN`. Class instances with named placeholders still work as params objects. (#22)
- `stringToSQLIdentifier` quotes with backticks for MariaDB too, not only `mysql` / `aurora-mysql`. (#21)
- `applyOrder` / `applyOrderFilter` order by the database column of the field (`@Column({ name })`): `{ field: 'createdAt' }` with `@Column({ name: 'created_at' })` is ordered by `"created_at"`. Previously the property name was used and the query failed (`column user.createdAt does not exist`). An unquoted `alias.property` is still left to TypeORM, which maps it itself. (#26)
- Typed methods work before `from()`: on a query created without an entity (`dataSource.createQueryBuilder()`, `qb.subQuery()`), `alias.column` keys (`selectTyped<{ base: Message }>(q => q.base.chatRoomId)`) no longer throw TypeORM's `Main alias is not set`; a single-level key there throws a `TypeError` that says to call `from()` first. (#24)
- On UPDATE / DELETE, an `alias.column` key naming the main alias (`u => u.user.firstName`) gives the bare column `"firstName"`, like a single-level key; it used to give `"user"."firstName"`, which PostgreSQL rejects. (#24)
- `selectTyped` with an array of callbacks keeps `useQuotes`, and no longer changes a `KeyHolder` passed in; `orderByTyped` / `addOrderByTyped` honor `options.useQuotes` for a `KeyHolder` selection. (#24)
- String fields of the untyped methods (`whereIsIn` / `whereIsNotIn`, `whereIsAny`, array / JSON / distinct-from where methods, `applyPeriodFilter`, `orderByArrayPosition`) are resolved through the query's aliases: a column of an alias is quoted by the driver whatever its name (`'user.first-name'` → `"user"."first-name"`, also on UPDATE / DELETE as `"first-name"`), and `alias.property` is mapped to its column (`'user.createdAt'` → `"user"."created_at"`). Other fields use the driver's quotes, so MySQL / MariaDB get backticks instead of double quotes, which MySQL reads as strings. `tableHelper.column()` always quotes the column as one identifier. (#28)
- `GetManyWithTotalsOptions` includes the pagination options. `getManyWithTotals` already honored `useTakeAndSkip`, but its type didn't allow it, so TypeScript code couldn't page queries with joined collections correctly. (#29)
